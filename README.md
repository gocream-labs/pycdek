# PyCDEK 2

Python library for CDEK API v2.0

API - [ru][api_url_ru] [en][api_url_en]



## Roadmap

Библиотека давно не обновлялась, поэтому актуализация разбита на этапы и два
мажорных релиза.

**2.0.0 - этапы 0-4.** Публичное API остаётся ровно таким же, как в текущей бете
`2.0.0b9`: сигнатуры методов, имена аргументов, типы возвращаемых значений и
текущие (в том числе ошибочные) реакции на ошибки не меняются. Код, работающий с
`2.0.0b9`, продолжит работать без единой правки. Смысл релиза - снять
четырёхлетнюю бету и привести в порядок сборку, тесты, линтеры и документацию,
ничего не ломая пользователям.

**3.0.0 - этап 5.** Всё ломающее: исправление ошибок в самом API, недостающие
эндпоинты, переименования параметров. Отдельный мажорный релиз, потому что
обновиться на него без правок в своём коде уже не получится.

Порядок не случайный: сначала появляется то, чем можно проверять изменения, потом
фиксируется текущее поведение, и только после этого что-то правится.


### 0. Инфраструктура

Модуль `pycdek/` не трогаем вообще - только обвязка вокруг, иначе нечем
контролировать последующие этапы.

* [x] Исключения в `.gitignore` - правило `.*` игнорирует все дотфайлы, из-за чего
	невозможно закоммитить `.github/`, `.pre-commit-config.yaml` и остальные конфиги.
	Само правило нужное (`.DS_Store`, `.venv`, `.idea/`), поэтому не убираем его, а
	добавляем точечные исключения. Блокирует всё остальное, поэтому идёт первым

Инструментарий - [hatch][hatch] (менеджер проекта, [PyPA][pypa]) и `hatchling`
(бэкенд сборки).

* [x] `setup.py` + `setup.cfg` + `MANIFEST.in` → единый `pyproject.toml`
	([PEP 621][pep_621]), бэкенд `hatchling`. Старые файлы удалены: секция
	`[isort]` была нерабочей (опция `not_skip` удалена в isort 5),
	`[wheel] universal = 1` относится к py2/py3-совместимым колёсам,
	`[bdist_rpm]` ссылался на несуществующий `INSTALL`, а `MANIFEST.in` при
	сборке через hatchling не используется вовсе
* [x] Версия литералом `__version__` в `pycdek/__init__.py`. Прежняя
	`get_version()` вычисляла её из кортежей на лету - такое значение не умеет
	переписывать `semantic-release` при релизе, а `hatchling` пришлось бы читать
	через `source = "code"`. Публичные `version` и `__VERSION__` сохранены
	алиасами, снаружи ничего не изменилось
* [x] Dev-зависимости в `[dependency-groups]` ([PEP 735][pep_735]), а не в
	`optional-dependencies` - тогда они не попадают в метаданные пакета и не видны
	пользователям
* [x] Лицензия объявлена строкой SPDX ([PEP 639][pep_639]) вместо вольного
	текста в `setup.py`, classifier `License ::` и устаревшего ключа
	`license-file` из `setup.cfg`. Сам файл `LICENSE` никуда не делся - он
	по-прежнему едет в пакете, теперь через `license-files`
* [x] Актуализировать метаданные пакета: имя без пробела, `requires-python`,
	`readme` с указанием content-type (без него PyPI не отрендерит README),
	корректные classifiers
* [x] `Development Status` из `3 - Alpha` в `4 - Beta` - соответствует текущей
	`2.0.0b9`
* [x] Отдельные окружения `lint` / `test` / `mtest` с **прибитыми** версиями
	инструментов вместо встроенных `hatch check` и `hatch test`. Встроенные тянут
	`ruff` и `pytest` из внутренних окружений hatch, и при обновлении самого hatch
	те молча меняются - CI краснеет без единой правки в коде
* [x] Настроить статический анализ. Правила выбраны широко, но часть отключена
	до своего этапа роадмапа, поэтому проверка зелёная уже сейчас. По сути список
	`ignore` - это машинно-проверяемый бэклог
* [x] Матрица тестов 3.10-3.14 - отдельные `tox` / `nox` не нужны
* [x] Запрет сетевых вызовов из тестов (`pytest-socket`)
* [ ] `pre-commit`, чтобы локальные проверки и CI не расходились. Локально можно
	гонять через `prek` - тот же формат конфига, заметно быстрее
* [ ] Хук на `commit-msg`, валидирующий формат gitmoji + скоуп: CHANGELOG теперь
	собирается из сообщений коммитов, и кривой коммит молча выпадет из релизных
	заметок

Команды:

```sh
hatch run init             # настройка локального репозитория
hatch run lint:check       # статический анализ
hatch run lint:fmt-check   # проверка форматирования
hatch run lint:format      # автоисправление и форматирование
hatch run test:check       # тесты с покрытием
hatch run mtest:check      # вся матрица 3.10-3.14
hatch version              # текущая версия
hatch build                # sdist + wheel
```

> **Форматирование отложено.** `hatch run lint:fmt-check` сейчас предлагает переписать
> ~250 строк: в файлах-справочниках схлопнется ручное выравнивание колонок, в
> `client.py` перестроится стиль с висячими словарями в аргументах. Это
> отдельный коммит, ничего больше в нём не меняя, с добавлением SHA в
> `.git-blame-ignore-revs` - иначе `git blame` по проекту перестанет быть
> пригодным. До тех пор в CI гоняем `lint:check`, но не `lint:fmt-check`.
>
> Туда же отложена пересортировка импортов (`I001`): в `client.py` сложилась
> раскладка «`from ...` перед `import ...`», и её правка смешалась бы с
> содержательными изменениями.


### 1. Тесты текущего поведения

Задача этапа - не «сделать хорошо», а **зафиксировать как есть**. Без этого на
следующих этапах невозможно отличить «сломал» от «оно и так не работало».

* [ ] Моки HTTP (`responses`) для всех реализованных методов
* [ ] Собрать фикстуры реальных ответов с тестового контура `api.edu.cdek.ru` -
	это единственное, что нельзя восстановить по коду постфактум
* [ ] Golden-тесты на сборку URL и на очистку payload (`clear_dict`)
* [ ] Тесты на известные баги из этапа 5 - с явным комментарием, что поведение
	зафиксировано намеренно


### 2. Модернизация до Python 3.10+

Изменения синтаксические, рантайм не затрагивают.

* [ ] `Optional[X]` → `X | None`, `List`/`Dict`/`Tuple` → `list`/`dict`/`tuple`,
	выпилить лишние импорты из `typing`
* [ ] Убрать `# -*- coding: utf-8 -*-` - в Python 3 это дефолт
* [ ] Проставить аннотации там, где их нет - **строго по факту**, а не по тому, как
	должно быть; иначе это скрытое изменение контракта
* [ ] `@typing.overload` по флагу `origin_response` - методы возвращают `dict` либо
	`Response` в зависимости от него, и это единственный способ описать такое честно,
	не трогая рантайм
* [ ] `py.typed` - **последним пунктом этапа**: после его появления аннотации
	становятся публичным контрактом, и любая неточность превращается в баг у
	пользователей

Нижняя граница 3.10 означает, что `enum.StrEnum` (появился в 3.11) недоступен.

Версия и CHANGELOG считаются [python-semantic-release][psr] по gitmoji в
коммитах - одним инструментом, а не связкой из двух. Гибрид «PSR считает
версию, gitmoji-changelog рисует CHANGELOG» рассматривался и отклонён: два
парсера одной истории держат две независимые таблицы эмодзи, которые со
временем расходятся, плюс это тянет Node в CI Python-библиотеки.

```sh
hatch run release:preview     # что получится, ничего не записывая
```

Уровень повышения можно задать флагом, если автоматики недостаточно:

```sh
semantic-release version --major            # 2.0.0
semantic-release version --major --as-prerelease   # 2.0.0-rc.1
semantic-release version --minor            # 1.5.0
```

**С первым релизом две отдельные тонкости.**

PSR отсчитывает от последнего *стабильного* тега и линию `2.0.0bX` за точку
отсчёта не берёт - без флагов он предлагает `1.4.6` (от тега `1.4.5` за апрель
2022). Флаг `--major` даёт ровно `2.0.0`, так что вручную тегировать не нужно.

Вторая тонкость - формат записи версии. PSR работает в SemVer, где пререлиз
отделяется дефисом, а в файле был PEP 440 - `2.0.0b9`. Регексп PSR матчил только
часть `2.0.0` и заменял её, оставляя хвост:

| было | флаг | стало |
|---|---|---|
| `2.0.0b9` | `--major` | `2.0.0b9` - замена ничего не изменила |
| `2.0.0b9` | `--minor` | `1.5.0b9` - версия испорчена |
| `2.0.0-b.9` | `--minor` | `1.5.0` - чисто |

Поэтому версия в `pycdek/__init__.py` записана как `2.0.0-b.9`. При установке
PEP 440 нормализует её обратно в `2.0.0b9`, так что имена артефактов и версия в
метаданных пакета не изменились:

```
dist/pycdek_2-2.0.0b9-py3-none-any.whl        Version: 2.0.0b9
```

Единственное отличие - атрибут `pycdek.__version__` в рантайме теперь отдаёт
`2.0.0-b.9`, а не `2.0.0b9`.

Дальше PSR генерирует собственный формат (`2.0.0`, `2.0.0-rc.1`), который его же
регексп разбирает целиком, и цикл самосогласован.

За историю до 2.0.0 CHANGELOG придётся написать руками: коммиты старше
`2.0.0b9` формату не соответствуют и попадут в раздел «Other».

## Develop

Настройка локального репозитория:

```sh
hatch run init
```

Проект использует [GitHub Flow][github_flow]: одна долгоживущая ветка, изменения
приходят через pull request, релиз выпускается по тегу.

Ранее использовался [git flow][git_flow_atlassian] с ветками `master` и
`develop`. От него отказались: релизные ветки и ветка разработки оправданы,
когда параллельно поддерживают несколько версий силами команды, а здесь это
только удваивало конфигурацию CI и требовало обратных слияний после каждого
релиза.

Если понадобится чинить 2.x после выхода 3.0.0, ветку поддержки удобнее завести
разово, чем держать всю машинерию git flow постоянно.

Коммиты - в формате gitmoji со скоупом:

```
✨ (client): Add order update method
🐛 (utils): Fix clear_dict on nested lists
```

От формата зависит и версия следующего релиза, и содержимое CHANGELOG, поэтому
он проверяется хуком на `commit-msg`.



## Release & Versioning

Версионирование по [semver][semver].

Версия лежит литералом в `pycdek/__init__.py`. Оттуда её читает `hatchling`
(`hatch version`) и туда же её записывает `semantic-release` при релизе -
поэтому вычислять её на лету, как раньше, больше нельзя.

Следующая версия определяется автоматически по gitmoji в коммитах с прошлого
тега: `💥` поднимает мажорную, `✨` - минорную, остальное - патч.

> Перед стабильным релизом выпускаем *rc*-версию для проверки обновления.

Планируемые релизы описаны в [Roadmap](#roadmap): 2.0.0 сохраняет текущее API,
3.0.0 приносит ломающие изменения.
